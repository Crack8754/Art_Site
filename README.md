# Artas

Artas — головна сторінка візуальної платформи для митців і поціновувачів мистецтва. Концепція натхненна стрічкою Pinterest: відвідувачі можуть відкривати роботи, зберігати їх та переходити до публікації власного арту.

## Можливості

- Адаптивна головна сторінка українською мовою.
- Hero-секція з ключовою цінністю платформи та статистикою.
- Стрічка реальних робіт із категоріями, переглядом деталей та пагінацією по 20 робіт.
- Публікація зображень у Supabase Storage; роботи відображаються у стрічці та профілі автора.
- Реєстрація та вхід через Google або email, підтвердження email, відновлення пароля й вихід через Supabase Auth.
- Публічні профілі з обмеженням доступу на рівні рядків (RLS).
- Профіль митця: аватар, `@username`, bio, локація, готові категорії напрямів, посилання та підписки.
- Вбудований Node.js HTTP-сервер без зовнішніх залежностей.

## Технології

- HTML5
- CSS3 (адаптивність, анімації, CSS Grid)
- Vanilla JavaScript
- Node.js (вбудований модуль `http`)
- Supabase Auth і PostgreSQL (підключаються окремо)

## Запуск локально

Потрібен Node.js 18 або новіший.

```bash
npm start
```

Після запуску відкрийте [http://localhost:3000](http://localhost:3000) у браузері.

## Підключення авторизації Supabase

Поточний репозиторій містить клієнтський інтерфейс авторизації та SQL-схему профілів. Для реальної роботи потрібен власний Supabase-проєкт і налаштування нижче:

1. Створіть Supabase-проєкт. Скопіюйте `public/auth-config.example.js` до `public/auth-config.js` і вкажіть Project URL та publishable/anon key з налаштувань API. `auth-config.js` ігнорується Git. **Не використовуйте в браузері `service_role` key.**
2. Виконайте `supabase/schema.sql` в SQL Editor проєкту. Це створить профілі, підписки, тригер створення профілю та RLS-політики: профілі можна читати публічно, змінювати — лише власний.
3. У Supabase Auth увімкніть підтвердження email і Google provider. Для Google OAuth створіть OAuth credentials у Google Cloud і внесіть їх у налаштування провайдера Supabase.
4. У Auth URL Configuration додайте Site URL та дозволені redirect URLs для локального сайту (`http://localhost:3000/**`) і домену розгорнутого сайту. У Google Console callback URL має відповідати URL, який показує Supabase для Google provider.
5. Для production налаштуйте власний SMTP-сервер і ліміти Auth. Для CAPTCHA створіть Turnstile або hCaptcha ключі, додайте secret у Supabase Auth Bot and Abuse Protection і розкоментуйте відповідні `captcha` налаштування у `public/auth-config.js` з site key. Форми підтримують віджет і передають одноразовий токен для входу email/пароль, реєстрації та відновлення пароля.
6. Налаштуйте мінімальну довжину пароля в Supabase не менше 12 символів. Supabase зберігає паролі як bcrypt-хеші; це безпечне хешування з сіллю, але воно не відповідає зазначеній у handoff вимозі Argon2id. Якщо Argon2id є обов’язковою вимогою, потрібен інший серверний механізм автентифікації або провайдер, який підтверджує цю схему.

Сесії керуються SDK Supabase з PKCE, оновленням токенів і збереженням сесії у браузері. Доступ до таблиць бази має обмежуватися RLS-політиками; не додавайте захищені операції лише на основі стану інтерфейсу. Для серверних API у майбутньому потрібна перевірка JWT на сервері.

## Завантаження артів і категорії

### Оновлення: до 5 зображень в одній роботі

Після попередніх SQL-файлів виконайте `supabase/artwork-images.sql` у Supabase SQL Editor, потім Ctrl + F5. Для нової бази порядок такий: `schema.sql` → `artworks.sql` → `artwork-images.sql`. Якщо повторно виконуєте старий `artworks.sql`, обов’язково повторіть також `artwork-images.sql`, щоб відновити політики для кількох фото.

Форма приймає від 1 до 5 зображень: обирайте кілька одразу або додавайте наступні окремо. Кожне має власне прев’ю та кнопку видалення; перше є обкладинкою. Назва, опис і категорія спільні для всієї роботи. Ліміт 10 МіБ і 40 Мп застосовується до кожного файлу. Стрічка, профіль і вікно перегляду підтримують гортання стрілками, крапками, клавішами ←/→ (коли фокус у галереї) та горизонтальним свайпом. Для одного фото навігація прихована.

Міграція додає `artworks.images` (масив JSON із `path`, `width`, `height`), перевіряє 1–5 фото, порядок шляхів, розміри й відповідність обкладинки. Старі записи з `images = NULL` читаються через попередні поля й не потребують перезавантаження файлів. Запис публікації створюється лише після завантаження всіх фото. Якщо сталася помилка посеред добірки, повторна спроба пропускає вже завантажені файли; скасування прибирає неопубліковані фото добірки. RLS забороняє видалення будь-якого фото опублікованої роботи, а не лише обкладинки.

Міграцію та роботу з реальною віддаленою базою потрібно перевірити у вашому Supabase; локальні тести використовують mock-клієнт.

Після `supabase/schema.sql` виконайте **`supabase/artworks.sql`** у SQL Editor того самого Supabase-проєкту. Скрипт можна виконувати повторно. Він створює таблицю `artworks`, публічний bucket `artworks`, індекси та RLS-політики. До виконання SQL стрічка показуватиме помилку, а публікація не працюватиме. Потім оновіть сайт через Ctrl + F5.

1. Увійдіть і натисніть «Опублікувати» — відкриється `upload.html`.
2. Оберіть від 1 до 5 JPEG, PNG або WebP, кожне до 10 МіБ і 40 мегапікселів. Браузер декодує зображення, зменшує довгу сторону до 4096 px і перетворює на WebP. Оригінал не зберігається; анімація не зберігається, метадані не переносяться.
3. Вкажіть назву (2–120 символів), категорію, необов’язковий опис (до 2000 символів) і підтвердьте право публікації.
4. Опублікована робота з’явиться на головній та у вкладці «Роботи» профілю. Лічильник робіт береться з бази.

Напрями профілю тепер обираються прапорцями: Живопис, Цифрове мистецтво, Фотографія, Ілюстрація, Скульптура, Колаж, 3D-арт, Графіка. Можна вибрати кілька або жодного. Арт має одну категорію з того самого списку. Список у `public/artworks.js` та SQL повинен залишатися узгодженим. Старі довільні напрями автоматично не переписуються: редактор попереджає про них; під час збереження залишаться лише обрані готові категорії.

Під час мережевої помилки «Повторити публікацію» використовує той самий UUID і шляхи, щоб не створювати дублікати. «Скасувати завантаження» перевіряє, чи публікація вже існує, і видаляє лише неопубліковані файли. Не закривайте вкладку до завершення: стан повторної спроби зберігається лише в пам’яті. Після примусового закриття можуть залишитися файли без запису; адміністратор може прибрати їх через Storage API лише після перевірки відсутності посилань як у `artworks.image_path`, так і в усіх елементах `artworks.images`.

### Доступ і обмеження

- Читати опубліковані роботи та зображення може кожен. Навіть завантажений, але ще не опублікований файл доступний за прямим URL: це публічне сховище, не місце для приватних матеріалів.
- Авторизований користувач може завантажувати у власну папку та створювати записи лише від свого імені. База перевіряє назву, опис, категорію, розміри й відповідність шляху автору та UUID; bucket обмежує файл до 10 МіБ і MIME `image/webp`.
- Опубліковані файли не можна перезаписати або видалити через клієнт. Редагування/видалення артів, модерація та приватні чернетки не реалізовані.
- Обробка зображення у браузері не замінює серверну перевірку байтів: прямий API-клієнт може її обійти. Перед широким публічним запуском потрібні серверна перевірка зображень, квоти, обмеження частоти та модерація.
- Node.js роздає статичні файли; дані передаються безпосередньо до Supabase під захистом RLS. Секретний `service_role` ключ не потрібен.

### Перевірки

```bash
npm test
```

Тести без зовнішніх залежностей перевіряють валідацію, обробку зображень і повторні спроби публікації на mock-клієнті. Вони не замінюють перевірку RLS у вашому Supabase. Після застосування SQL перевірте публікацію власним акаунтом, появу роботи в стрічці та профілі, фільтр категорії та перегляд без входу. Іншим акаунтом перевірте, що він не може публікувати від чужого імені або видалити чужий файл.

## Нотатки

Після оновлення профілів повторно виконайте `supabase/schema.sql` у SQL Editor. Скрипт додає перевірки username, bio та локації також до існуючої таблиці й створює відсутні профілі для старих акаунтів, не перезаписуючи наявні. Обмеження `NOT VALID` перевіряють нові та змінені записи; старі записи автоматично не виправляються. Після застосування оновіть сторінку через Ctrl + F5.

У профілі кнопка ⚙ відкриває налаштування акаунта. «Змінити пароль» показує форму без переходу на головну: поточний пароль (якщо використовується), новий пароль від 12 символів та його підтвердження. Зміна виконується через Supabase Auth `updateUser`; SQL-схему оновлювати не потрібно. Якщо Supabase вимагає свіжу сесію, вийдіть і увійдіть повторно. Пароль акаунта Google ця форма не змінює.

Декоративні зображення головної сторінки залишаються демонстраційними. Стрічка та роботи профілю використовують Supabase. Пошук, збереження робіт і колекції залишаються недоробленими та не входять до реалізації завантажень.
